# Очереди, джобы, события и планировщик

Проверь по коду и `config/queue.php`, что уже принято в проекте (драйвер, Horizon, имена очередей, базовые классы джобов), и следуй этому. Точный API — `search-docs` для установленной версии и `rules/queue-jobs.md`, `rules/events-notifications.md`, `rules/scheduling.md` скилла `laravel-best-practices`.

## Что выносить в очередь

| Выносить | Почему |
|---|---|
| Любой вызов внешнего API (кроме чтения, без которого нельзя ответить, — и тогда с коротким таймаутом) | чужая задержка и сбои не должны держать HTTP-запрос и воркер веб-сервера |
| Письма, SMS, push, уведомления (`ShouldQueue` у Mailable и Notification) | доставка медленная и ненадёжная |
| Обработка файлов: изображения, видео, импорт/экспорт, PDF, архивы | долго и много памяти |
| Массовые операции над многими записями, пересчёты, денормализация | не укладываются во время запроса; делятся на чанки |
| Вебхуки входящие: обработка после быстрого ответа 2xx | провайдер ждёт секунды и повторяет при таймауте |
| Побочные эффекты события, которые не нужны для ответа пользователю (аналитика, индексация поиска, кэш) | ответ не ждёт второстепенного |

Оставлять синхронно: проверку прав и валидацию, запись основной сущности, которую пользователь сразу видит, чтение для ответа. Правило-ориентир: всё, что может занять больше ~1 с или упасть по чужой вине, — в очередь, а пользователь видит статус операции (`pending` → `done`/`failed`) и получает результат уведомлением или опросом.

## Проектирование джоба

- **Имя очереди** по классу работы и приоритету (`default`, `mail`, `media`, `integrations`, `payments`): медленная очередь не задерживает быструю. Несколько очередей — несколько воркеров или приоритеты Horizon.
- **`$tries` / `retryUntil()`**, **`$backoff`** (массив нарастающих задержек: `[10, 60, 300]`), **`$timeout`**, **`$maxExceptions`**. `retry_after` соединения очереди обязан быть больше `$timeout`, иначе джоб выполнится дважды параллельно.
- **Идемпотентность обязательна**: любой джоб может выполниться повторно (ретрай, `retry_after`, перезапуск воркера после частичной работы). Джоб проверяет состояние перед действием и действует атомарно (idempotency-and-consistency.md).
- **Уникальность**: `ShouldBeUnique` (+ `uniqueId()`, `$uniqueFor`) — не ставить в очередь второй такой же джоб, пока первый не выполнен; `ShouldBeUniqueUntilProcessing` — снимается при старте. Не путать с идемпотентностью: уникальность снижает дубли, но не исключает повтор.
- **Middleware джобов**: `WithoutOverlapping($key)` — не выполнять параллельно для одной сущности; `RateLimited` — лимит провайдера; `ThrottlesExceptions` — пауза после серии сбоев внешней системы (простой предохранитель).
- **Данные джоба**: передавай ID или модели (`SerializesModels` перечитает модель при выполнении); не передавай большие массивы и секреты. Модель удалена к моменту выполнения — `$deleteWhenMissingModels` или явная проверка.
- **`failed(Throwable $e)`**: что делать после исчерпания попыток — статус сущности `failed`, уведомление пользователю или человеку, компенсирующее действие. Окончательный сбой не должен молча теряться: таблица `failed_jobs`, алерт.
- **После коммита**: джоб, поставленный внутри транзакции, может выполниться раньше коммита и не найти данных. Используй `->afterCommit()` / `ShouldQueueAfterCommit` (или `after_commit` в конфиге соединения), для событий — `ShouldDispatchAfterCommit`.
- **Цепочки и пакеты**: `Bus::chain` — строгий порядок шагов с остановкой при сбое; `Bus::batch` — много однотипных работ с прогрессом, `then`/`catch`/`finally` и `allowFailures()` по необходимости. Шаги цепочки тоже идемпотентны.
- **Длинные работы** дели на чанки (`chunkById`, `lazyById`) по джобу на чанк, а не один джоб на час.

## События и уведомления

- Событие — факт, случившийся в модуле («`OrderPaid`»), слушатели — побочные эффекты других модулей. Слушатели с внешними вызовами — `ShouldQueue`.
- Событие, которое должно увидеть закоммиченные данные, — `ShouldDispatchAfterCommit`.
- Слушатель тоже идемпотентен: событие может прийти повторно при ретрае.
- Критичный для бизнеса побочный эффект (списание, выдача доступа) не прячь в слушателе события без гарантии доставки — делай явным шагом Action или через outbox (idempotency-and-consistency.md).

## Планировщик

- `withoutOverlapping()` — задача не стартует, пока идёт предыдущая; `onOneServer()` — при нескольких серверах (нужен общий кэш); тяжёлое — `runInBackground()` или постановка джобов.
- Задача планировщика ставит джобы, а не делает тяжёлую работу сама.
- Задача идемпотентна: пропущенный или повторный запуск не ломает данные (выбирай записи по состоянию, а не «за последний час»).

## Наблюдаемость очередей

- Horizon (если есть) или `queue:monitor` с порогом длины очереди; алерт на рост `failed_jobs`.
- Логи джоба с контекстом (ID сущности, попытка, ключ идемпотентности); `Context` переносится из запроса в джоб.
- Команда или запрос, которым человек находит застрявшие операции (`pending` дольше N минут), и способ их повторить.

## Тесты

- `Queue::fake()` / `Bus::fake()` — что джоб поставлен с нужными данными и в нужную очередь; отдельный тест выполнения джоба (`handle`) с проверкой идемпотентности: два выполнения — один результат.
- Тест `failed()` и поведения при исключении внешней системы.
