# Внешние API и вебхуки: отказоустойчивость

Внешняя система всегда может ответить медленно, ошибкой, неожиданными данными или не ответить вовсе; её лимиты и формат меняются без нас. Проектируем так, чтобы её сбой не ломал наш продукт и не терял данные. Точный API — скилл `agentio-saloon` (клиенты без SDK), документация SDK, `rules/http-client.md` и `rules/error-handling.md` скилла `laravel-best-practices`.

## Один адаптер на систему

- Адаптер — `App\Integrations\<Система>\…` (каталог `app/Integrations/<Система>`, имя системы в PascalCase; правило проекта при любой раскладке остального кода, один неймспейс на систему, даже если ею пользуются несколько доменов; тесты — `tests/Feature/Integrations/<Система>/…`) — единственное место вызовов: базовый URL, аутентификация, таймауты, ретраи, лимиты, логирование, преобразование ответов в DTO и ошибок — в свои исключения (`<Система>Unavailable`, `<Система>Rejected`). Остальной код не видит HTTP.
- Настройки — `config/services.php` из `.env`; секреты не попадают в логи и исключения.
- Ответы валидируются: отсутствующее поле или неизвестный статус — понятное исключение, а не `null` в глубине кода.

## Клиент: SDK или Saloon

Правило проекта (полностью — скилл `agentio-saloon`, «Правило проекта: SDK или Saloon»):

- У системы есть готовый поддерживаемый PHP SDK (официальный или общепринятый пакет сообщества с релизами за последний год, поддерживающий версии PHP и Laravel проекта) — адаптер в `App\Integrations\<Система>` оборачивает SDK, типы SDK наружу не выходят. SDK ещё не установлен — его установка вопрос человеку (новая зависимость, SKILL.md «Зависимости»: варианты «SDK» и «Saloon» с рекомендацией); до ответа проектируй всё, что от него не зависит.
- Готового SDK нет (заброшен, не поддерживает версии проекта, не покрывает нужные операции) — интеграция пишется на **Saloon** (`saloonphp/saloon`), не голый `Http::`, не Guzzle, не curl: `<Система>Connector` (базовый URL, аутентификация, таймауты, ретраи, лимиты) и по Request-классу на операцию (`…\Integrations\<Система>\Requests\…`), ответы — в DTO. Saloon заранее одобрен владельцем: решение — ADR (при первой интеграции), установка — отдельная первая TASK эпика (`composer require saloonphp/saloon --no-interaction`; плагины — `saloonphp/*` по необходимости). Как строить коннекторы, запросы, пагинацию, лимиты и тесты — скилл `agentio-saloon`.
- Точный API Saloon — README и исходники `vendor/saloonphp/*` установленной версии и docs.saloon.dev (`WebFetch`): `search-docs` его не покрывает.

## Таймауты и ретраи

- Всегда `connectTimeout` и `timeout` (секунды, а не дефолт). Сумма таймаутов всех попыток меньше `$timeout` джоба и времени запроса пользователя.
- Ретраи — только для безопасных или идемпотентных вызовов (GET, вызовы с ключом идемпотентности провайдера) и только для временных ошибок: соединение, 408, 429, 5xx. 4xx (кроме 408/429) — ошибка данных, не повторяем.
- Backoff нарастающий с jitter; 429 — уважать `Retry-After`.
- В джобе ретраи даёт очередь (`$tries`, `$backoff`), в HTTP-клиенте — 1–2 быстрых повтора; не перемножай одно на другое без расчёта.

## Где вызывать

- Изменяющие и медленные вызовы — в джобах (queues-and-jobs.md); пользователь получает статус, а не ждёт.
- Никогда внутри транзакции БД: откат не отменит внешний эффект, а транзакция держит блокировки, пока ждёт сеть. Порядок: запись намерения в БД → коммит → вызов в джобе → запись результата (или outbox, idempotency-and-consistency.md).
- Синхронный вызов в запросе пользователя — только чтение, без которого нельзя ответить, с коротким таймаутом и деградацией.

## Сбой и деградация

Для каждой интеграции в статье фичи записано, что видит пользователь и что происходит с данными, когда система недоступна:
- **отложить** — операция в очереди, повторится; пользователь видит «в обработке»;
- **деградировать** — показать кэшированные или неполные данные, отключить зависимую функцию;
- **отказать** — понятное сообщение пользователю, без потери введённых данных.
- **Предохранитель (circuit breaker)**: после серии сбоев перестать звать систему на время (`ThrottlesExceptions` у джобов или счётчик в кэше в адаптере), чтобы не исчерпать воркеры и лимиты.
- Лимиты провайдера: `RateLimited` у джобов, `RateLimiter` в адаптере; массовые операции — пачками.

## Входящие вебхуки

- Отдельный маршрут без CSRF и сессии; проверка подписи / секрета / источника до любой обработки; защита от повтора по метке времени, если провайдер её даёт.
- Событие сохраняется с уникальным `(source, event_id)` → дубль отбрасывается; быстрый 2xx; обработка в джобе, идемпотентная.
- Порядок не гарантирован: обработчик сверяет состояние, а не применяет событие вслепую; при сомнении — запрашивает актуальное состояние у системы.
- Для пропущенных вебхуков — сверка по расписанию (опрос статуса у системы).

## Данные и контракт

- Внешние ID хранятся в своих колонках с уникальным индексом `(system, external_id)`.
- Справочные данные внешней системы кэшируются с явным TTL и сбросом.
- Персональные данные, передаваемые во внешнюю систему, перечислены в статье фичи (и в «Общих требованиях», если это новый получатель).

## Наблюдаемость

- Лог каждого вызова: система, операция, длительность, код ответа, ID нашей сущности, ключ идемпотентности; без тел с секретами и персональными данными.
- Алерт на долю ошибок или открытый предохранитель; видно, сколько операций ждёт повтора.

## Тесты

- Фейки клиента, а не реальная сеть: для Saloon — `MockClient`/`MockResponse` (или `Saloon::fake()` плагина Laravel) и запрет реальных запросов (`Config::preventStrayRequests()`; `Http::fake()` запросы Saloon не перехватывает); для SDK — его фейки. Ответы: успех, 4xx, 5xx, 429 с `Retry-After`, таймаут, неожиданный формат.
- Проверка отправленного запроса (`$mockClient->assertSent(...)` / `Saloon::assertSent`): заголовки, ключ идемпотентности, тело.
- Вебхук: валидная и невалидная подпись, дубль, неверный порядок.
- Поведение продукта при недоступности системы (сообщение, статус, повтор).
