# Идемпотентность и согласованность данных

Идемпотентная операция при повторе с теми же данными даёт тот же результат и не создаёт второго эффекта. Повторы неизбежны: двойной клик, повтор запроса клиентом или прокси после таймаута, ретрай джоба, повторный вебхук, перезапуск планировщика, ручной повтор человеком. Точный API — `search-docs`, `rules/eloquent.md`, `rules/migrations.md`, `rules/caching.md` скилла `laravel-best-practices`.

## Что обязано быть идемпотентным

- Каждый джоб, слушатель событий и задача планировщика.
- Каждый обработчик входящего вебхука.
- Каждая операция с деньгами, выдачей доступа, отправкой во внешнюю систему, отправкой письма о значимом событии.
- Каждый API-эндпоинт, который создаёт сущность и может быть повторён клиентом (мобильное приложение, интеграция): с ключом идемпотентности.
- Создание сущности из формы — защита от двойной отправки на сервере (блокировка кнопки в интерфейсе — только удобство).

## Приёмы (от простого к сложному)

1. **Уникальное ограничение в БД** — последняя линия защиты, работает при любой гонке: `unique(order_id)` у платежа, `unique(provider, external_id)` у события вебхука, составной `unique(user_id, date)`. Вставка — `insertOrIgnore`, `upsert` или `createOrFirst` (опирается на уникальный индекс); `firstOrCreate` без уникального индекса гонку не закрывает.
2. **Переход состояния условным обновлением**: `update ... where id = ? and status = 'pending'` и проверка числа изменённых строк. Кто изменил строку — тот и выполняет эффект; второй видит 0 и выходит. Состояния — enum, разрешённые переходы описаны в статье фичи (жизненный цикл сущности).
3. **Ключ идемпотентности** для запросов извне: клиент присылает `Idempotency-Key`; сервер хранит ключ (уникальный индекс), хэш тела и результат; повтор с тем же ключом и телом возвращает сохранённый ответ, с другим телом — 409/422. Срок хранения ключей описан.
4. **Блокировки**: `Cache::lock("order:{$id}")->block(5, ...)` (атомарные блокировки — общий кэш: Redis, БД; не `file`/`array` на нескольких серверах) — короткая критическая секция вокруг проверки и действия; `lockForUpdate()` внутри транзакции — для строк, которые читаются и меняются вместе (баланс, остаток); оптимистическая блокировка (колонка `version`, `update ... where version = ?`) — когда конфликт редок.
5. **Outbox**: если нужно атомарно изменить БД и отправить сообщение или вызвать внешнюю систему — запиши намерение в таблицу outbox в той же транзакции, а отправку делает идемпотентный джоб, который отмечает запись отправленной. Так эффект не теряется при сбое после коммита и не дублируется.

## Транзакции

- Транзакция — короткая: только записи в БД, которые должны быть атомарными. Никаких HTTP-вызовов, писем и ожиданий внутри (длинные блокировки, а откат БД не откатит внешний эффект).
- Джобы и события, порождённые в транзакции, — после коммита (`afterCommit`, `ShouldDispatchAfterCommit`).
- Агрегаты, которые меняются конкурентно (баланс, счётчик, остаток), — атомарный `increment`/`decrement` с условием или `lockForUpdate`, не «прочитать → посчитать в PHP → записать».
- `DB::transaction($fn, attempts)` повторяет при deadlock — тело тоже должно быть повторяемым.

## Сбой посередине

Для каждой многошаговой операции опиши в статье фичи: на каком шаге может оборваться процесс, что останется в БД и что доведёт операцию:
- **повтор** — шаги идемпотентны, джоб повторяется;
- **сверка** — периодическая задача находит операции, застрявшие в промежуточном состоянии дольше N минут, и доводит или откатывает их (обязательна для денег, см. payments.md);
- **компенсация** — обратное действие для уже сделанного шага (возврат, отзыв доступа), когда шаги нельзя сделать атомарными.

## Конкурентность в интерфейсе

- Два пользователя редактируют одну сущность — последний затирает первого? Если это недопустимо — версия в форме и 409 при конфликте.
- Лимиты и квоты («не больше 3 активных») проверяются атомарно в БД, а не подсчётом перед вставкой.

## Тесты

- Повтор: тот же запрос, джоб или вебхук дважды — один эффект (одна запись, одно письмо — `Mail::fake()`, один вызов — `assertSentCount` фейка клиента).
- Повтор с ключом идемпотентности и другим телом — ошибка.
- Переход состояния из неразрешённого состояния — отказ без эффекта.
- Гонку надёжно воспроизвести в тесте трудно — поэтому защита держится на уникальных ограничениях и условных обновлениях, которые проверяются обычным тестом.
