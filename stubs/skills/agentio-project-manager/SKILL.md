# Project manager

Опирается на скилл agentio-youtrack-workflow (загрузи его первым): иерархия, статусы, захват, шаблоны, инструменты MCP. Не дублируй его — следуй ему. Шаблоны описаний: `../agentio-youtrack-workflow/references/issue-templates.md`.

## Вход

- ID идеи в `{{project}}` (`tag: idea`, `Stage: Backlog`), **или**
- идея, поставленная разработчиком в Telegram (в описании — «Идея поставлена разработчиком в Telegram»; текст может быть расшифровкой голосового: опечатки распознавания исправляй по смыслу, не додумывая требований) — планируется как любая другая, **или**
- текст от человека — тогда сначала создай идею: `create_issue(project="{{project}}", summary="[IDEA] …", description=<текст>, customFields={"Type": "Idea", "Stage": "Backlog"})`, метка `idea` (`manage_issue_tags`); «на потом», «пока не брать в работу» — ещё и метка `parked`.

**Отложенная идея** — у идеи есть метка `parked`. Шаги 1–3.1 те же (захват, требования, аналитик в режиме отложенной идеи), шаги 3.2–6 не выполняются — раздел «Отложенная идея» ниже.

## Процедура планирования

### 1. Захват и контекст
1. `php artisan agentio:yt claim <IDEA> --as=pm --plan="Планирование идеи"`. При `LOST` (код 3) — остановись.
2. `update_issue(<IDEA>, customFields={"Stage": "Analysis"})` (claim ставит In Progress; для идеи фаза называется Analysis).
3. Контекст идеи (agentio-youtrack-workflow, раздел 7): `get_issue`, все комментарии. Если идея возвращена из `Blocked` — сначала обработай ответы человека по разделу «Вопросы к человеку» скилла agentio-youtrack-workflow (ответы в статьи, `[AGENT:DECISION]`), затем продолжай с шага, на котором планирование остановилось. Прочитай статьи «Обзор продукта» ({{kb.overview}}), «Глоссарий» ({{kb.glossary}}), карту модулей «Системной аналитики» ({{kb.analysis}}; дерево — `php artisan agentio:yt kb-tree {{kb.analysis}}`) и существующие эпики (`search_issues "project: {{project}} Type: Epic"`), чтобы не дублировать сделанное.

### 2. Требования
Сформулируй и запиши в описание идеи (раздел `## Требования`, через `update_issue`, не затирая исходный текст):
- **Цель** — какую проблему решаем.
- **Пользователи** — роли.
- **Границы** — что делаем и что явно НЕ делаем.
- **Критерии успеха** — проверяемые.

**Нехватка данных.** Если без ответа человека нельзя определить существенное (бизнес-правило, роль, объём, деньги, внешнюю систему, юридические ограничения), не додумывай — но и не останавливайся на первом вопросе: запиши требования, которые от ответа не зависят, проведи аналитику (шаг 3.1, аналитик соберёт свои вопросы) и задай все вопросы одним `[AGENT:BLOCKED]` в идее по разделу «Вопросы к человеку» скилла agentio-youtrack-workflow (варианты, рекомендация, Stage для возврата — `Backlog`), затем `php artisan agentio:yt release <IDEA> --state=Blocked` и остановись. Мелкие технические детали и пробелы с безопасным умолчанием — допущения, их фиксирует `[AGENT:DECISION]`.

### 3. Аналитика и архитектура — до декомпозиции на TASK
1. Примени скилл **agentio-system-analyst** к идее: статьи модулей и фич созданы или обновлены (включая особенности системы — повторы, сбои, долгие операции, деньги), карта модулей актуальна, сводка влияния записана в идею. Если аналитик задал вопросы (`[AGENT:BLOCKED]`) — остановись: эпики не создаются до ответа.
2. Набросай эпики (обычно 1; больше — только если части дают ценность независимо). Создай EPIC: `create_issue(project="{{project}}", summary="[EPIC] …", customFields={"Type": "Epic", "Stage": "Analysis"})`, связь `relates to` с идеей (`link_issues`), описание по шаблону.
3. Примени скилл **agentio-laravel-architect** к каждому эпику: решения в разделах «Архитектура» статей фич и модулей, ADR при необходимости, **порядок реализации и параллелизм** в описании эпика. Это вход для шага 5. Отдельная статья на эпик не создаётся.

### 4. Декомпозиция
Для каждого эпика:
1. STORY — по одному пользовательскому сценарию (обычно — сценарий из статьи фичи; в «Контексте» ссылка на статью). Критерии приёмки Given/When/Then, включая негативные и авторизацию; они покрывают правила `FR`/`BR` фичи, относящиеся к сценарию. `create_issue(project="{{project}}", parentIssue=<EPIC>, customFields={"Type": "Story", "Stage": "Analysis"})`. TASK создаются так же: `parentIssue=<STORY>`, `"Type": "Task"`.
2. TASK — атомарные изменения внутри STORY по шаблону (контекст, что сделать, критерии приёмки, ссылки на статьи и решения `AD-n`, оценка затрагиваемых областей, вне рамок). Требования надёжности из `[AGENT:DECISION]` архитектора (повтор запроса, ретрай джоба, сбой внешней системы, дубль вебхука) — проверяемыми критериями приёмки той TASK, которая реализует операцию. Тест на атомарность: одна цель без «и»; выполнима субагентом без вопросов за один заход; есть проверяемый результат. Тесты пишутся **в той же задаче**, что и код (зелёный `composer test` — условие сборки), отдельные TASK «написать тесты» не создаются.
3. Типовая нарезка для Laravel: миграция и модель → Action (сервис) и Form Request → контроллер и маршрут → джоб или событие → представление, страница или компонент фронтенда (стек проекта — см. `CLAUDE.md` и ADR-001). Каждая — TASK, если по объёму не тривиальна; тривиальные соседние шаги склеивай.
4. **Первые TASK эпика из «Порядка реализации» архитектора** (agentio-laravel-architect, разделы «Внешние платформы» и «Зависимости»), каждая в первой по смыслу STORY:
   - «Скилл платформы <X>» — эпик затрагивает внешнюю платформу или сервис (Telegram-бот, Telegram Mini App, VK Mini App, MAX, PWA, …), для которой в `.claude/skills` нет скилла: разработчик создаёт `.claude/skills/<платформа>-development/` по скиллу `agentio-platform-skill`. Все TASK по платформе зависят от неё, в их «Контексте» — ссылка на скилл;
   - «Установить Saloon» — первая интеграция без SDK по ADR (`composer require saloonphp/saloon --no-interaction`); TASK интеграции зависят от неё.
   Других пакетов в задачах нет: новая зависимость — только после ответа человека.

### 5. Зависимости
1. По порядку от архитектора: `link_issues(target=<зависимая>, linkType="depends on", issueToLinkId=<от которой зависит>)`.
2. **Пересечения по файлам.** Для каждой пары задач, у которых пересекаются «затрагиваемые области» (тот же файл, `routes/web.php`, `composer.json`/`composer.lock`, общая миграция или модель, общий компонент), добавь `depends on` в порядке реализации, даже без логической зависимости. Это защита от конфликтов при параллельной работе. Все новые миграции эпика выстраивай в цепочку.
3. Межэпиковые зависимости: на уровне EPIC → EPIC.

### 6. Валидация и Ready
1. `php artisan agentio:yt validate <IDEA>` — без проблем (нет циклов, у каждой TASK родитель STORY, у STORY — EPIC, префиксы совпадают с Type, нет пустых STORY).
2. Переводи в `Ready` (`update_issue(<ID>, customFields={"Stage": "Ready"})`) **только полностью описанное**: TASK с заполненными разделами шаблона, STORY с критериями приёмки, EPIC с аналитикой и архитектурой. Порядок: TASK → STORY → EPIC.
3. Повторно `validate`: первая волна готовых задач не пуста (иначе ошибка в зависимостях).
4. `php artisan agentio:yt tree <EPIC>` — вставь вывод в `[AGENT:DONE]`.
5. Идея: `[AGENT:DONE]` (эпики, статьи, первая волна задач) → `php artisan agentio:yt release <IDEA> --state=Done`.

## Отложенная идея

Метка `parked` значит: человек хочет понять идею, но пока не брать её в разработку.
1. Захват, контекст и требования — шаги 1 и 2 как обычно (вопросы — тоже как обычно, одним `[AGENT:BLOCKED]`).
2. Примени **agentio-system-analyst** в режиме отложенной идеи (его раздел «Отложенная идея»): анализ записывается в статью «Идея <ID>: …» под «Идеями» ({{kb.ideas}}) и строку таблицы «Идей», статьи «Системной аналитики» не меняются.
3. Эпики, архитектура и декомпозиция **не делаются**.
4. `[AGENT:DONE]` в идею: «**Идея проанализирована и отложена.** Статья: <ID статьи>. Затрагивает: <модули и фичи со ссылками>. Оценка объёма: <…>. Взять в работу: снять метку `parked` и вернуть Stage в `Backlog` (или «бери в работу <ID>» в Telegram-боте)». Затем `php artisan agentio:yt release <IDEA> --state=OnHold`.

**Отложенная идея взята в работу** — метки `parked` нет, идея в `Backlog`, а в комментариях есть `[AGENT:DONE]` «Идея проанализирована и отложена»: это обычное планирование, но шаг 3.1 начинается с переноса анализа (agentio-system-analyst, раздел «Отложенная идея принята в разработку»). Требования из описания идеи и статьи идеи сверь с текущим продуктом: за время ожидания он мог измениться.

## Сопровождение

Запускается из `/agentio-status`, `/agentio-dispatch` или по запросу человека:
- **Пересчёт блокировок:** `php artisan agentio:yt blocked`. Ready-задачи, ждущие незакрытых зависимостей, — норма. Задачи, ждущие зависимость в `Blocked`, — эскалируй в `[AGENT:BLOCKED]` у первопричины.
- **Разбор `[AGENT:BLOCKED]`:** если человек ответил комментарием после блокировки, а Stage не вернул — обработай ответы по разделу «Вопросы к человеку» скилла agentio-youtrack-workflow (в статьи и описание, при необходимости перестрой задачи, `[AGENT:DECISION]`) и верни Stage, указанный в `[AGENT:BLOCKED]` (`update_issue(<ID>, customFields={"Stage": "Ready"})`; идею — `Backlog`). Если ответа нет — ничего не делай: молчание без возврата Stage не согласие.
- **Изменение требований:** сначала статья фичи (через agentio-system-analyst), потом задачи. Уже сделанные TASK не переписывай — создавай новые.
- **Закрытие** (`update_issue(<ID>, customFields={"Stage": "Done"})` с комментарием `[AGENT:DONE]`): STORY → `Done`, когда все её TASK в `Done`, STORY прошла review и эпик слит в `{{base_branch}}`. EPIC → `Done`, когда все STORY в `Done` и критерии успеха выполнены. Слияние подтверждай: `git fetch origin {{base_branch}}`, затем `git branch -r --contains <ID> --list origin/{{base_branch}}` или `gh pr list --head <ID> --state merged` (ветка эпика начатого прежней версией agentio — `epic/<ID>-*`). Эпик попадает в `{{base_branch}}` только через pull request, который сливает человек (панель `/agentio`, `php artisan agentio:accept <ID>` или Telegram-бот agentio); релиз `{{base_branch}}` в `{{production_branch}}` — pull request, который сливают после подтверждения разработчика. Сам ничего не сливай.

## Чек-лист самопроверки

- [ ] Требования: цель, пользователи, границы, критерии успеха записаны в идею.
- [ ] Существенные пробелы не додуманы, а заданы все сразу одним `[AGENT:BLOCKED]` с вариантами и рекомендацией; ответы человека перенесены в статьи.
- [ ] agentio-system-analyst и agentio-laravel-architect отработали **до** создания TASK.
- [ ] Каждая TASK атомарна, по шаблону, со ссылками на статьи и оценкой затрагиваемых файлов.
- [ ] Задачи с общими файлами или миграциями связаны `depends on`.
- [ ] `validate` без проблем, первая волна не пуста.
- [ ] В Ready — только полностью описанное. Идея закрыта `[AGENT:DONE]` и `agentio:yt release`.
- [ ] Отложенная идея (`parked`): только требования и анализ в «Идеях», без эпиков; `[AGENT:DONE]` и `release --state=OnHold`.
